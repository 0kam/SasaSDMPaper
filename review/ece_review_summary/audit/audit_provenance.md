# Artefact provenance and clean-run reproducibility audit

Scope: whole repository — `data/`, `ortho/`, `results/`, `scripts/`, `.gitignore`, git history.
Repo audited: `/Users/okamoto/NIES/SasaSDMPaper` (main worktree; data present).
Public remote: `https://github.com/0kam/SasaSDMPaper.git`, branch `main`, HEAD `48decbd`.

Everything below was executed. Commands and outputs are quoted inline.

Throughout I distinguish:
- **(a)** what the code as written would do on a clean run,
- **(b)** what the archived artefacts show actually happened,
- **(c)** what the manuscript says was done.

---

## 0. Executive summary

1. **The headline snowmelt number (−0.86 d/yr, "8.6 days per decade") cannot be
   reproduced from the archived inputs, and is inconsistent with the snowmelt rasters
   actually fed to the models.** `ortho/data/snow/snow_reg.tif` has mean −0.8636 (matches
   the manuscript). The per-pixel slopes implied by the `fitted_*.tiff` rasters that the
   SDMs actually used have mean **−0.7147** (r = 0.51 between the two surfaces). The code
   that supposedly wrote `snow_reg.tif` cannot run (`partit`, `$coeffisients`) and writes
   to a different directory than where the file lives.
2. **A clean end-to-end run is impossible from the public repo.** The georectification
   look-up table `ortho/data/georectified.csv`, on which `ortho/georectify.R` and
   `scripts/vegetation_classification/utils/interpolate.R` both depend, does not exist
   anywhere; the code that produced it exists only as shell history in the tracked
   `ortho/.Rhistory`, and references a Linux HDD path.
3. **A clean run would silently change the model.** `sdm_tbm.R`/`sdm_tdm.R` glob
   `data/terrain_features/*.tif`. That directory now contains `twi.tif`, which is in
   **none** of the fitted models and in none of the manuscript. `preprocess_snow_data.R`
   writes `snow_mean/sd/reg.tif` **into that same directory**, so running the pipeline in
   its natural order injects 3 further predictors. A cloner re-running `sdm_tdm.R` today
   gets a 9–12 predictor model, not the published 8.
4. **`sdm_tbm.R` as written trains only Random Forest** (GAM/MaxEnt/XGB commented out) and
   saves/loads `models_wo_dist_twi.rds`, a file that does not exist. The archived
   `models_wo_dist.rds` contains all four algorithms. The published TBM cannot be
   regenerated by the published TBM script.
5. **Two archived copies of the TBM test metric disagree** (`tss_score_tbm.csv`
   TSS = 0.5556, published; `tss_score_tbm.rds` TSS = 0.5348, stale). Several published
   figures differ byte-wise **and substantively** from the archived `ortho/figures/`
   versions (variable-importance rank order is not the same).
6. `ortho/data/tateyama2.tiff` (156 MB) is a **truncated, unreadable TIFF**.
7. Publication hygiene: `ortho/.Rhistory` (tracked, public) exposes an external HDD path
   and the undocumented georectification method; the deleted `paper/` tree — including
   `covering_letter.doc` with the author's institutional e-mail — is still recoverable
   from public git history.

### 2.3 `preprocess_snow_data.R` lines 118-137 cannot run

The block that supposedly produces `snow_reg.tif`:

```r
118  library(multidplyr)
119  s <- snow_reg %>%
120    group_by(x, y) %>%
121    partit
122    summarise(
123      lm.coef = (lm(snowmelt ~ year, data = .))$coeffisients["year"],
124      lm.r2 = (lm(snowmelt ~ year, data = .))$adj.r.squared,
...
```

The file *parses* (34 top-level expressions), so this is a runtime failure, not a syntax
error — a small correction to the prior lead:

```
$ Rscript -e 'p <- parse("scripts/sdm/preprocess_snow_data.R"); cat("parses OK:", TRUE, " n exprs:", length(p))'
parses OK: TRUE  n exprs: 34
$ Rscript -e 'library(dplyr); d <- tibble::tibble(x=1,y=1); d %>% group_by(x,y) %>% partit'
Error: 関数 "partit" を見つけることができませんでした    # could not find function "partit"
```

`%>% partit` is parsed as the call `partit(.)`; it errors. `s` is therefore never created,
so `snow_reg_ras` (line 128) and `write_stars(..., "data/terrain_features/snow_reg.tif")`
(line 137) cannot execute. Additionally `$coeffisients` is a typo for `$coefficients` and
`$adj.r.squared` is not a member of an `lm` object (it lives on `summary(lm)`), so even
with `partition(cluster)` restored the block would return `NULL`s.

**Conclusion: `snow_reg.tif` was produced by code that no longer exists in the
repository.** See §2.5 for the numerical consequence.

### 2.5 The stale snow rasters — the most consequential finding

`snow_mean.tif`, `snow_sd.tif`, `snow_reg.tif` all have the identical valid-cell count
1 133 175 and live in `ortho/data/snow/`, not in `data/terrain_features/` where the code
writes them. I re-ran the documented logic of `preprocess_snow_data.R` (§2.3 aside)
faithfully — `read_stars` + `st_warp(vege_2012_5x5.tiff)` over `data/snow/raw/*.tiff`,
`drop_na()` over years, `snowmelt > 0`, per-pixel OLS on `year`:

```
cells: 3157153
after drop_na: 1206233
snow_mean recomputed mean: 170.4257          archived snow_mean: 171.7633  (n 1133175)
snow_sd   recomputed mean: 10.3557           archived snow_sd  :   9.6773  (n 1133175)
snow_reg  recomputed mean (all): -0.7147     archived snow_reg :  -0.8636  (n 1133175)
  with adj.R2>0.2 (as coded): 75235 cells,  mean slope = -1.7183
  with raw  R2>0.2          : 185897 cells, mean slope = -1.5238
```

**None of the three archived rasters is reproducible from the archived raw inputs, under
any reading of the code.**

Cross-check against the rasters the models *actually* consumed:

```
slope implied by (fitted_2030 - fitted_2012)/18 : mean = -0.7147   n = 1206064
slope implied by (fitted_2021 - fitted_2012)/9  : mean = -0.7100   n = 1178220
archived snow_reg.tif                            : mean = -0.8636
cor(implied, archived) over 1105897 shared cells : 0.5106
```

So the `fitted_*.tiff` series **is** internally consistent with the 10-year archived raw
set (recomputed n = 1 206 233 vs `fitted_2012.tiff` n = 1 206 064; the 169-cell gap is the
`snowmelt > 0` filter), but `snow_reg.tif` **is not** — and `snow_reg.tif` is the file
whose mean (−0.8636) the manuscript reports:

> `paper/matmet.qmd:77` — "The mean regression coefficient was −0.86, corresponding to an
> advance of 8.6 days per decade."

The value implied by the rasters actually used in the models is **−0.715 d/yr = 7.1 days
per decade**, and the two surfaces correlate only r = 0.51.

Most plausible explanation (consistent with every number above but not directly
verifiable, because the missing `georectified.csv` prevents me from producing the 2010
raster): the snow summaries were computed over **11 years including 2010** —

### 3.1 The order-dependent hazard (glob collision)

`preprocess_snow_data.R:67,96,137` writes into `data/terrain_features/`; `sdm_tbm.R:13` and
`sdm_tdm.R:13` glob `data/terrain_features/*.tif`. Running Stage 5 before Stage 6 — the
only sensible order, since Stage 6 needs Stage 5's `fitted_*.tiff` — therefore injects
`snow_mean`, `snow_sd` and `snow_reg` as three extra predictors.

Number of `.tif` files globbed:

| scenario | files globbed | predictors after `snow` is added |
|---|---|---|
| archived models were fit with | 6 topographic (`aspect, roughness, slope, elevation, TPI, TRI`) | 7 (TBM) / 8 (TDM) |
| repo as it stands today | 7 (`+ twi`) | 8 / 9 |
| after running `preprocess_snow_data.R` | 10 (`+ snow_mean, snow_sd, snow_reg`) | 11 / 12 |

`snow_reg` in particular is a per-pixel *trend* and, in the 2030 scenario, would be held
constant while `snow` is extrapolated — an incoherent design that nobody intended. This is
the single most important thing to fix before any re-analysis.

There is a second, subtler glob hazard: `preprocess_snow_data.R:11` globs
`data/snow/raw/*.tiff`, and `georectify.R:62-63` writes into that directory from
`data/snow/aligned/`. Since `data/snow/aligned/` (public) contains **2010** and the archived
`raw/` does not, a clean run yields **11** snowmelt years, not the 10 the `fitted_*.tiff`
were built from, and not the "2011–2021" the manuscript claims.
